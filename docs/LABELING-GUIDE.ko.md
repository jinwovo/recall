# 라벨링 가이드 — 사실성(factuality) 인증서용 claim 판정

[English](LABELING-GUIDE.md) · **한국어**

[ADR 0017](adr/0017-claim-level-conformal-factuality.md)에서 코드가 대신할 수 없는 단 하나의
단계에 대한 매뉴얼입니다. 답변의 각 문장이 **그 답변을 생성할 때 참고한 문서(passage)로 뒷받침되는가**를
사람이 판정합니다. 이 판정이 보정(calibration) 데이터가 되고, 여기서 계산된 임계값으로 서빙이 claim을
보류합니다. **판정 습관이 몇 퍼센트만 어긋나도 임계값이 움직이며, 보증은 이 라벨만큼만 참입니다.**

## 작업 순서

```bash
# 1. observe 모드로 서빙: claim에 점수만 매기고 아무것도 보류하지 않음
RAG_FACTUALITY_ENABLED=true RAG_FACTUALITY_THRESHOLD=-1   # .env에 설정 후 스택 기동

# 2. 수집 — 답변당 한 행, 모든 claim이 "supported": null 상태
make collect-claims GOLD=beir-scifact/gold.jsonl          # eval/claims-to-label.jsonl 생성

# 3. 라벨링 — 이 문서

# 4. 인증 — 임계값과 붙여넣을 YAML 출력. 인증 불가면 0이 아닌 종료 코드
make certify-claims
```

각 행은 다음과 같습니다.

```json
{"query": "how does the cache stay bounded?",
 "passages": [{"n": 1, "source": "redis.md", "content": "..."},
              {"n": 2, "source": "cache.md", "content": "..."}],
 "claims": [{"text": "Entries expire after the configured TTL [2].", "score": 0.91, "supported": null},
            {"text": "Eviction uses LFU by default.", "score": 0.12, "supported": null}]}
```

모든 `null`을 `true` 또는 `false`로 바꿉니다. **라벨링하는 동안 `score`를 보지 마세요** — 열을 가리거나
점수를 지운 사본으로 작업하세요. 점수를 보고 단 라벨은 구조적으로 채점기와 일치하게 되고, 그 라벨로
계산한 임계값은 아무것도 인증하지 못합니다.

## 단 하나의 질문

> **나열된 `passages` 중 적어도 하나가 이 문장을 말하거나 직접 함축하는가?**

"사실인가", "그럴듯한가", "전문가라면 그렇게 말할까"가 아닙니다. 서빙이 하는 약속은 *모델이 본 것에
근거했는가*이므로, 라벨은 그것만 측정해야 합니다.

| 상황 | 라벨 | 이유 |
|---|:---:|---|
| 어떤 passage가 표현만 다르게 같은 말을 함 | `true` | 바꿔 말한 것도 근거 |
| 외부 지식 없이 한 passage에서 바로 따라 나옴 | `true` | "직접 함축" |
| 맞는 말이지만 어느 passage에도 없음 | **`false`** | 상식은 근거가 아님 — 가장 흔한 라벨링 실수 |
| 두 passage를 합쳐야 성립 | `true` | 채점기는 가장 좋은 단일 passage를 쓰므로 생각보다 드묾. 그래도 정직하게 판정 |
| 일부만 뒷받침되고 일부는 아님 | **`false`** | 한 부분이라도 근거가 없으면 근거 없는 claim — "Redis는 RDB와 AOF로 영속화하며 기본으로 켜져 있다"에서 "기본으로 켜짐"에 대한 내용이 없으면 `false` |
| 숫자·버전·이름·단위가 조금이라도 다름 | **`false`** | "30초"는 "30 ms"로 뒷받침되지 않음. "Kafka 3.6"은 "Kafka 3.5"로 뒷받침되지 않음 |
| 인용 `[n]`이 엉뚱한 passage를 가리키지만 다른 passage가 뒷받침 | `true` | 라벨은 내용에 대한 것. 인용 정확도는 별개 문제 |
| 인용은 맞는데 그 passage가 실제로는 그 말을 하지 않음 | **`false`** | 인용은 증거가 아님 |
| 단서를 단 주장 ("X는 Y를 일으킬 수 있다") | 주장 자체를 판정 | passage가 X가 Y를 일으킬 수 있다고 말할 때만 `true` |
| 확인할 주장이 없음 ("방법은 다음과 같습니다:", "선택지는 두 가지입니다:", "요약하면") | `true` | 거짓을 주장하지 않음. `false`로 달면 이유 없이 임계값만 올라감 |
| "I don't know based on the available documents" | — | 수집되지 않음. 답변 거부는 건너뜀 |
| 중간에 잘린 문장 (토큰 한도 도달) | 지금까지 주장한 것만 판정 | "기본 타임아웃은"은 아직 아무것도 주장하지 않음 → `true`. "기본 타임아웃은 5"는 값을 주장함 → 확인 |
| 코드, 명령어, 설정 키 | passage에 나오거나 그로부터 따라 나올 때만 `true` | 지어낸 플래그는 기술 문서 QA에서 가장 비싼 환각 |
| 1분 안에 판단이 안 됨 | **`false`** | 의심스러우면 안전한 쪽으로. 임계값이 약간 엄격해질 뿐, 느슨해지지 않음 |

## 지름길처럼 보이지만 아닌 것들

- **LLM으로 라벨을 미리 채우지 마세요.** judge는 이 보정이 독립적이어야 하는 바로 그 측정 도구입니다
  ([ADR 0015](adr/0015-prediction-powered-inference.md)). 양을 늘리려고 judge 라벨 세트를 만들 거라면
  별도로 두고 PPI로 사람 라벨과 결합하세요. 파일을 섞으면 안 됩니다.
- **어려운 행을 건너뛰지 마세요.** 애매한 답변을 빼면 서빙이 실제로 보게 될 것보다 쉬운 보정 세트가
  남고, 보증은 교환가능성(exchangeability)을 전제로 합니다. 대신 의심 규칙에 따라 `false`로 다세요.
- **`text`나 `score`를 수정하지 마세요.** 라벨만 고칩니다.

## 얼마나 필요한가

- **인증이 가능한 최소치**: `alpha = 0.10`에서 답변 9개 — 진술은 가능하지만 쓸모 있는 임계값은 아님.
- **권장**: 실제 트래픽이 묻는 질문에서 뽑은 답변 200–300개. 10개짜리 `gold.jsonl`은 너무 작고
  너무 깔끔합니다. BEIR SciFact의 300개 질의가 출발점으로 적당합니다.
- **시간**: 익숙해지면 claim당 약 15초, 답변당 claim 몇 개 — 답변 300개에 4–6시간을 잡으세요.
  한 번에 하기보다 여러 번 나눠서 하세요. 한 시간쯤 지나면 판정 품질이 떨어집니다.
- **도메인별**: `--by-group`으로 인증할 거라면 그룹마다 이 정도 크기의 표본이 따로 필요합니다.

## 라벨을 믿기 전에 확인할 것

1. 두 번째 사람이 무작위 10% 행을 첫 번째 사람의 라벨을 보지 않고 라벨링합니다.
2. 그 claim들에서 일치율을 계산합니다. **약 90% 미만이면 멈추세요**: 불일치는 거의 항상 이 가이드의
   규칙 하나를 두 가지로 읽은 결과입니다. 해소한 뒤 그 사례를 위 표에 추가하고, 그 규칙이 영향을 준
   행을 다시 확인하세요.
3. `make certify-claims`를 실행합니다. 인증서가 **vacuous**(뒷받침되는 claim의 20% 미만만 유지)로
   나오면, 채점기가 이 데이터에서 근거 있는 claim과 없는 claim을 구분하지 못한다는 뜻입니다. 라벨을
   늘려도 고쳐지지 않고, `alpha`를 느슨하게 하면 문제를 숨길 뿐입니다.

## 임계값을 배포한 뒤

임계값은 트래픽이 라벨링한 표본과 비슷한 동안만 유효합니다. `FactualityMonitor`가 judge 관점에서 이를
감시하다가 약속이 깨진 것이 확인되면 경고를 남깁니다(대시보드의 `recall_rag_factuality_alarming`).
알람이 울리면 숫자를 손으로 조정하지 말고, 현재 트래픽에서 새 표본을 수집해 다시 라벨링하세요.
